Architecture reference / Web chat

统一聊天界面技术架构

一个 Vite + React + AI Elements 聊天页面，嵌入多种业务前端；通过统一接入 API 连接 Mastra Agent，并把身份、会话、AI SDK 7 消息流和工具结果分层处理。

多系统 iframe 复用单点登录接入流式会话与工具卡片供后续实现参考
01 / DECISION

架构决策

业务系统保留自己的登录和页面技术栈；聊天产品独立发布。各系统只接入 iframe 与一次性的身份交接，聊天页统一承担会话体验。

A

一套前端

Vite + React + AI Elements 构建独立聊天页。React、Vue、HTML、JSP 页面都只嵌入同一地址。

B

一条接入链

业务后端确认原登录用户；接入层建立数字员工会话；Mastra 执行 Agent。

C

一个展示契约

接入 API 返回 AI SDK 7 UIMessage 流；React 组件按消息部件与工具名渲染。

D

清晰授权边界

接入许可、工具调用许可和目标系统最终授权分别校验，并保留审计记录。

已选技术路径：聊天页使用 @ai-sdk/react 的 useChat() 管理消息与流状态，AI Elements 负责展示。接入 API 在身份校验后返回 AI SDK 7 UIMessage 流；Mastra 侧使用 @mastra/ai-sdk 适配。iframe 接入和企业身份边界仍由接入层负责。
02 / TOPOLOGY

系统边界与职责

业务系统域

多套老系统，各自发布
React / Vue / HTML / JSP 页面显示入口、打开 iframe、处理尺寸与关闭事件
业务系统后端校验已有登录；为该用户申请短时、一次性接入凭据
边界 ①：现有业务登录只由业务系统判定

统一聊天产品域

集中开发、部署与升级
Vite + React + AI Elements 独立聊天页iframe 桥接、useChat 流状态、消息部件渲染、会话切换
数字员工接入 API / BFF凭据交换、会话认证、Agent 路由、流转发、历史读取、审计关联
边界 ②：聊天会话令牌与 conversationId 分离

Agent 与业务能力域

运行、调用和最终授权
Mastra Agent / Memory模型推理、工具意图、运行状态、会话记忆
企业工具网关逐次工具准入、目标凭据处理、限流、结果治理与审计
目标业务系统持有业务数据，并作最终数据与操作授权
边界 ③：Agent 可调用不代表目标业务已授权
宿主页面→聊天 iframe→接入 API→Mastra→工具网关→目标系统

这是逻辑责任划分，不要求每个方框单独部署。首期接入 API、Mastra 和工具网关可以按实际规模合并部署，但权限检查仍须分别执行。

03 / REQUEST ORDER

从打开页面到收到回答

加载聊天页

宿主页面嵌入统一聊天 URL。URL 只放非敏感配置，例如系统标识和界面模式；聊天页向父页面发出 CHAT_READY。

确认现有登录并申请接入

宿主页面调用自己的后端；后端根据原有业务会话确认用户，向数字员工接入层申请短时、一次性凭据。此步不创建聊天会话。

完成 iframe 身份交接

父页面定向发送 CHAT_BOOTSTRAP；iframe 校验来源后调用 POST /agent/auth/exchange。接入层建立数字员工会话并返回允许的 Agent 范围。

读取或新建 conversationId

聊天页读取归属于该用户的会话列表或创建新会话；conversationId 仅用于定位历史，不能代替身份凭据。

发送消息并接收流

聊天页的 useChat() 调用 POST /agent/chat/messages，携带数字员工会话凭据与 conversationId。接入层鉴权、路由到 Mastra，并返回 AI SDK 7 UIMessage 流。

逐次授权、渲染与留痕

工具网关和目标系统分别执行权限检查。useChat() 归并流状态；工具结果进入对应 React 组件；运行、拒绝和异常关联审计标识。

登录体验：目标是复用业务系统的既有登录，不让用户再登录一次。但 iframe 不会天然继承父页面 Cookie；接入凭据交换必须由已验证的业务后端与接入层共同完成。
04 / TRUST

iframe、会话与安全边界

跨窗口协议 拟定

{
  "v": 1,
  "type": "CHAT_BOOTSTRAP",
  "requestId": "opaque-id",
  "payload": { "oneTimeCode": "short-lived-code" }
}

约定 CHAT_READY、CHAT_BOOTSTRAP、CHAT_RESIZE、CHAT_CLOSE。父子窗口均校验 event.origin 和 event.source，发送时使用精确 targetOrigin。消息字段做运行时校验，避免重复提交。

凭据边界

数据用途处理方式
业务登录态业务系统识别原用户留在原系统；不得直接当作 Mastra 凭据
一次性接入码首次建立数字员工身份关联短期、单次、绑定用户/宿主/目标；不进 URL
数字员工会话每次聊天 API 鉴权由接入层验证；按部署条件选同站点 BFF 或短期令牌
conversationId定位聊天历史服务端校验归属；不视为授权凭据
目标系统凭据代表用户调用业务接口在工具网关/后端处理；目标系统仍作最终授权

浏览器与部署约束

嵌入许可

聊天页的响应设置 CSP frame-ancestors 宿主白名单；宿主页允许加载聊天页（如 frame-src）。检查现有 X-Frame-Options。

跨站点 Cookie

不同站点下，iframe Cookie 可能被浏览器限制。优先验证同站点代理/BFF；若采用浏览器持有短期令牌，须明确续期、退出与失效策略。

持续流连接

聊天消息是 POST 流式响应；代理须允许逐块输出，配置合理的空闲超时和取消传递。跨源调用仅对实际需要的来源开放 CORS。

05 / MESSAGE CONTRACT

流式消息协议

浏览器端采用 AI SDK 7 的 UIMessage 与消息流协议：useChat() 负责发送、增量更新、停止和错误状态，界面读取 messages[].parts。Mastra 原生 ChunkType 留在服务端，由 @mastra/ai-sdk 转换；首期不另造一套与 AI SDK 并行的浏览器事件封套。

明确匹配 AI SDK 7

// Mastra 服务端：在受保护的接入链后提供消息流
chatRoute({ path: '/chat/:agentId', version: 'v7' })

// React 聊天页：接入 API 对外暴露受保护的聊天路径
useChat({ transport: new DefaultChatTransport({
  api: '/agent/chat/messages'
}) })

version: 'v7' 选择 UI 消息流格式，并非 Agent 或模型版本。Mastra 的 chatRoute() 默认仍为 v5；新项目应显式指定 v7。示例路径为架构拟定，实际路径和鉴权方式以接入 API 实现为准。

消息部件与展示

UIMessage 部件界面职责验收重点
文本部件AI Elements 消息组件增量渲染完成、空回答、异常
工具部件按工具名及业务展示类型渲染状态与结果执行中、成功、失败、无权限
文件、来源等部件预览或展示受控链接类型、权限、过期处理
自定义数据部件承载需要扩展的业务展示数据服务端裁剪、类型校验、版本管理
接入约束：接入 API 必须先鉴权并校验 conversationId 归属，再将请求交给 Mastra。若它需要自定义转发、审计或消息处理，可用 handleChatStream() 实现同样的 v7 输出。历史消息恢复也须转换为匹配 v7 的 UIMessage；断线续传需要另行设计与验证。
06 / RENDERING

工具结果如何保证可见、可解释

1 · 工具定义

每个工具用 outputSchema 校验业务返回，避免缺字段或类型漂移。模型消费数据与界面展示数据分开：toModelOutput 面向模型，transform.display 可处理浏览器可见内容。

2 · 渲染注册表

React 以工具名及可选的 displayType + 版本 查找组件，例如状态卡、表格、图片、文件、审批。组件只接收经过服务端裁剪和前端校验的数据。

3 · 兜底与安全

未知类型显示“暂不支持的结果”与安全摘要，不静默丢弃。Markdown 做安全渲染；附件经受控 URL 获取；工具异常单独显示。

内容类别React / AI Elements 组件策略必须覆盖的状态
普通回答文本 / Markdown 组件增量、完成、失败、空回答
业务工具按 displayType 命中的专用卡片待执行、执行中、成功、失败、无权限
文件与图片预览、下载或受控链接加载失败、过期、无权限、类型未知
需人确认的动作审批/拒绝组件，回传显式决定待确认、已提交、已失效、重复点击
未知事件安全摘要与诊断编号保留 trace/runId 供排查

“渲染正确”必须由工具数据契约、流事件映射、组件注册和异常兜底共同保证；仅有 Agent 的最终文字不能覆盖全部工具输出。

07 / API & DEPLOY

接口建议与部署

接口（建议）调用方职责要点
POST /api/agent/access宿主页面 → 业务后端确认原业务登录并获取一次性接入码由服务端绑定用户、系统、有效期
POST /agent/auth/exchange聊天 iframe → 接入层兑换数字员工会话原子单次使用；校验宿主与允许的 Agent
POST /agent/chat/messages聊天 iframe → 接入层发送消息并返回 AI SDK 7 UIMessage 流鉴权、会话归属、取消与审计
GET /agent/chat/conversations聊天 iframe → 接入层读取本用户会话列表服务端按用户过滤
GET /agent/chat/conversations/{id}/messages聊天 iframe → 接入层恢复历史消息历史转换为相同的 UI 展示模型
POST /agent/chat/tool-decisions聊天 iframe → 接入层提交需确认工具的决定按 runId/toolCallId 校验权限和时效

以上路径是架构建议，不代表当前仓库已实现。真正的路由、身份格式和错误码应在接入层接口评审后定稿。

新聊天项目的依赖基线

位置依赖与版本约束用途
聊天前端Vite + TypeScript + React 19；ai@7 与兼容的 @ai-sdk/reactuseChat()、消息状态与流传输
界面组件AI Elements + shadcn/ui + Tailwind CSS 4消息、工具和输入组件；按需安装组件
Mastra 服务端@mastra/ai-sdk >= 1.9.0；聊天路由显式 version: 'v7'将 Agent 输出转换为 AI SDK 7 UI 消息流
运行环境Node.js 22+、ESM；提交依赖锁文件满足 AI SDK 7 运行要求并固定可复现安装

Vite 前端与 Mastra 服务可分别开发、发布；浏览器只能调用受保护的接入 API。实际安装以稳定版依赖与锁文件为准，不使用预发布版本。

推荐部署形态

统一域名承载聊天静态资源与接入 API，例如 chat.company.example。各业务系统仅配置 iframe 地址及宿主白名单；接入 API 在服务端调用 Mastra。代理对聊天流关闭缓冲、保留逐块响应。

跨站点 Cookie 的可用性要按实际域名和目标浏览器验证；同站点反向代理方案可作为部署选项。

配置与版本治理

聊天页版本集中发布；iframe 桥接协议单独带版本，UI 消息流固定为 AI SDK 7 契约。业务自定义数据和工具展示类型分别版本化。宿主系统使用可配置 Agent/主题/语言，不允许自行指定未经授权的用户或工具权限。

发布需支持灰度与回滚；记录宿主系统、前端版本、AI SDK 流契约版本及 Agent 版本，便于追踪问题。

08 / DELIVERY

实施顺序与验收

阶段 1 · 最小只读闭环

选一个业务系统、一个只读工具；完成已有登录 → iframe 接入 → 数字员工会话 → Mastra → 工具网关 → 目标系统授权 → 结果卡片 → 审计。

阶段 2 · 多系统复用

固化宿主接入脚本、白名单、配置项与版本策略；验证 React、Vue、HTML/JSP 至少各一条真实嵌入路径。

阶段 3 · 完整交互

加入历史恢复、取消、附件、审批、失败重试和运维指标。新工具按 schema 与渲染注册流程接入。

上线前验收清单

  • 未登录、已退出及超时用户无法继续使用聊天
  • 伪造 postMessage 来源或重放接入码被拒绝
  • 无权用户无法读取他人的 conversationId
  • 工具未授权及目标系统拒绝均有明确反馈与审计
  • 文本、工具、文件、未知类型及错误均可展示
  • 流式输出可取消，代理不缓存至结束才返回
  • 跨站点 Cookie 受限时仍有明确可用方案
  • 各业务系统 CSP / X-Frame-Options 与 iframe 尺寸通过实测
  • 历史消息刷新后与实时渲染语义一致，均符合 AI SDK 7 UIMessage
  • 浏览器最低版本覆盖实际老旧系统用户
